### Task 2.2: `ParcelaRepository.ts` — CRUD + tombstone + validaciones

- **Files (create):**
  - `mobile/src/repositories/ParcelaRepository.ts`
- **What:**
  - Espejar el shape de `GroupRepository` (post-16-01): exports nombrados, result types discriminados, `notifyDataChanged()` después de cada mutation.
  - Funciones públicas (cada una ≤20 líneas — extraer helpers si excede; CLAUDE.md §3):
    - `findById(id: string, opts?: { includeDeleted?: boolean }): Promise<Parcela | null>` — por default filtra `deletedAt IS NULL`; `includeDeleted: true` es uso INTERNO del sync (no exponer a screens).
    - `findByPlantacion(plantacionId: string): Promise<Parcela[]>` — ordena por `createdAt ASC`, filtra `deletedAt IS NULL`.
    - `create(params: { plantacionId, nombre, codigo, descripcion?, usuarioCreador }): Promise<CreateParcelaResult>` — uppercase del `codigo` (mismo pattern que `createGroup`), valida unicidad y descripcion, inserta con `pendingSync: true`, `createdAt: localNow()`, `updatedAt: localNow()`, `deletedAt: null`, `id: Crypto.randomUUID()`.
    - `update(id, params: { nombre, codigo, descripcion? }): Promise<UpdateParcelaResult>` — valida unicidad excluyendo `id` y excluyendo tombstoneados, valida descripcion, actualiza `updatedAt: localNow()` + `pendingSync: true`. Rechaza con `not_found` si la parcela está tombstoneada.
    - `delete(id: string): Promise<DeleteParcelaResult>` — **soft-delete por tombstone** (D-16-19):
      1. Verificar que la parcela existe y NO está ya tombstoneada (`deletedAt IS NULL`); si no existe → `{ deleted: false, error: 'not_found' }`.
      2. Contar `groups WHERE parcela_id = id AND (deleted_at IS NULL OR FALSE)` — los grupos no tienen tombstone en este phase, así que cuenta todos. Si `> 0`, retornar `{ deleted: false, error: 'has_children', childCount }`.
      3. Si 0 grupos hijos: `UPDATE parcelas SET deleted_at = localNow(), pending_sync = true, updated_at = localNow() WHERE id = ?`. Retornar `{ deleted: true }`. `notifyDataChanged()`.
    - `restore(id: string): Promise<RestoreParcelaResult>` — usado por sync conflict recovery: `UPDATE parcelas SET deleted_at = NULL, pending_sync = true, updated_at = localNow() WHERE id = ?`. Valida que la restauración no cause colisión de unicidad con otra parcela activa de la misma plantación (si hay colisión → `{ restored: false, error: 'nombre_duplicate' | 'codigo_duplicate' | 'both_duplicate' }`).
    - `markPendingSync(id: string): Promise<void>` — `pendingSync = true`, `updatedAt: localNow()`, notify.
    - `markSynced(id: string): Promise<void>` — `pendingSync = false`, notify. (Usado por pushService en 16-03.) Aplica también a tombstones: una vez que el server confirma el delete, se limpia el flag pero `deletedAt` queda persistido.
    - `getSyncableParcelas(plantacionId: string): Promise<Parcela[]>` — espejo de `getSyncableGroups`; retorna parcelas con `pendingSync=true` (incluye tombstoneadas — el sync de delete debe poder subirlas). Por eso esta función NO filtra `deletedAt IS NULL`.
  - Helper privado: `validateParcelaUniqueness(plantacionId, nombre, codigo, excludeId?)` — espejo exacto de `validateGroupUniqueness` (post-16-01). **Filtra `deletedAt IS NULL`** (parcelas tombstoneadas no son colisión). Retorna `'codigo_duplicate' | 'nombre_duplicate' | 'both_duplicate' | null`.
  - Helper privado: `validateDescripcion(descripcion?: string | null)` — si `descripcion && descripcion.length > 10000`, retorna `'descripcion_too_long'`; si no, `null`.
  - Types exportados:
    - `interface Parcela { id, plantacionId, nombre, codigo, descripcion: string | null, pendingSync, createdAt, updatedAt, deletedAt: string | null }`.
    - `CreateParcelaResult = { success: true; id: string } | { success: false; error: 'codigo_duplicate' | 'nombre_duplicate' | 'both_duplicate' | 'descripcion_too_long' | 'unknown' }`.
    - `UpdateParcelaResult` análogo + posible `'not_found'` (parcela tombstoneada o inexistente).
    - `DeleteParcelaResult = { deleted: true } | { deleted: false; error: 'has_children'; childCount: number } | { deleted: false; error: 'not_found' }`.
    - `RestoreParcelaResult = { restored: true } | { restored: false; error: 'not_found' | 'nombre_duplicate' | 'codigo_duplicate' | 'both_duplicate' }`.
- **Why:** PCRD-01, PCRD-04, PCRD-05, PCRD-06, PCRD-07; D-16-06, D-16-07, D-16-08, D-16-09, D-16-19.
- **Verification:**
  - `npx tsc --noEmit mobile/src/repositories/ParcelaRepository.ts` → 0 errores.
  - Cada función exportada tiene ≤20 líneas (medir con `awk` o lectura visual).
  - Tests unitarios de Task 2.5 cubren tombstone path: delete → fila persiste con deletedAt set; restore → fila vuelve a aparecer.

## Risks & Mitigations

1. **Riesgo:** Duplicación entre `ParcelaRepository.findByPlantacion` y `parcelaQueries.listByPlantacion`. **Mitigación:** Decisión explícita en Task 2.3 — el repo expone la versión "raw"; `parcelaQueries` expone la versión "con stats" (no duplica, agrega). Re-export si fuera necesario.
2. **Riesgo:** Tests usan el mismo `integrationDb` harness y pueden contaminarse entre tests si no se limpia FK-ordered. **Mitigación:** En `beforeEach`, borrar en orden `trees → groups → parcelas → plantations` (mismo pattern que `subgroup-lifecycle.test.ts`). El reset debe usar DELETE físico (no soft-delete) para limpiar tombstones también.
3. **Riesgo:** `descripcion` con caracteres Unicode multi-byte (emojis, acentos): `String.length` cuenta code units (UTF-16), no caracteres. Si el server CHECK cuenta bytes, hay drift. **Mitigación:** Documentar en el repo que la validación usa `String.length` (code units) — coincide con la implementación del CHECK constraint en P15 (`LENGTH(descripcion) <= 10000` en Postgres cuenta caracteres). Caso edge muy poco probable a 10k chars; aceptar el drift.
4. **Riesgo:** El field `usuarioCreador` no existe en `parcelas` (verificable en schema), pero `getSyncableParcelas` originalmente tenía firma `(plantacionId, userId?)`. **Mitigación:** La firma final es `(plantacionId)` solamente; filtrar solo por `pendingSync=true` y `plantacionId`. Documentar en el repo: "Parcelas no tienen creador — todos los técnicos asignados pueden editarlas (la auditoría queda en server-side `created_by` si existe)".
5. **Riesgo:** La migration 0012 olvida actualizar `migrations.js` (lección Phase 13). **Mitigación:** Task 2.1 explícitamente enumera los 3 archivos a tocar; la verification step #1 (app arranca sin splash hang) detecta inmediatamente la regression.
6. **Riesgo:** El harness `integrationDb` no aplica la nueva migration automáticamente (depende de cómo cargue `migrations.js`). **Mitigación:** Verificar en Task 2.5 antes de escribir tests; si el harness usa `drizzle-orm/expo-sqlite/migrator` con el `migrations` import, la migration 0012 se aplica automáticamente al `migrate()`. Si el harness tiene un setup manual, agregar el step.
