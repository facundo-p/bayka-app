## Goal

Extender `SyncService` (`pullService` + `pushService`) para sincronizar parcelas bidireccional preservando los invariantes de FK e idempotencia, e incluyendo **propagación del tombstone (`deleted_at`)** introducido en 16-02:
- **pull baja parcelas ANTES que groups** (groups tienen FK a parcelas);
- **push sube parcelas ANTES que groups** (idem);
- **tombstones se propagan en ambos sentidos**: local→server (push de parcela con `deleted_at != null`) y server→local (pull marca `deleted_at` y no resurrecciona la fila);
- **conflict de unicidad al subir** (nombre/código duplicado en otra parcela de la misma plantación) deja la parcela local con `pending_sync=true` y devuelve error claro al usuario sin limpiar el flag (memory `feedback_state_lifecycle_audit.md`). El classifier de errores se ancla en el shape estable de postgres (`code === '23505'`, parseo de `details`) — capturado en un spike previo a la implementación.

Propagar `pending_sync` de parcelas al agregador OrangeDot en `usePendingSyncCount` para que la `PlantationCard` muestre el punto cuando cualquier cosa abajo (parcela, grupo, árbol) está pendiente. Validar todo con un test de integración E2E con SQLite real: crear/borrar parcela offline → reconectar → server alineado; modificar/tombstonear server → pull → local alineado; intentar subir duplicado → error + flag persiste.

## Success Criteria

Mapeo a ROADMAP Phase 16 success criteria:

- [ ] **(SC#2 / D-16-21)** Migration Supabase `014_parcelas_deleted_at.sql` aplicada en el ambiente donde corre el E2E (local Supabase o staging): `SELECT column_name FROM information_schema.columns WHERE table_name='parcelas' AND column_name='deleted_at'` retorna 1 fila.
- [ ] **(SC#5)** Sync de parcelas funciona online y offline:
  - Online: `pullFromServer` trae parcelas del server vía Supabase para las plantaciones del usuario, con `ON CONFLICT REPLACE` y respeto a tombstones locales pendientes.
  - Offline: parcela creada/borrada con `ParcelaRepository` queda con `pending_sync=true`; tras reconexión, `pushToServer` la sube (incluyendo `deleted_at`) y limpia el flag.
- [ ] **(SC#5)** Orden FK respetado: pull `parcelas` antes de `groups`; push `parcelas` antes de `groups`. Verificable en código y en el log de sync.
- [ ] **(SC#6)** Conflict detection: si server rechaza por unicidad (nombre o código duplicado en otra parcela de la misma plantación), el cliente:
  - NO limpia `pending_sync` (queda en `true` — memory `feedback_state_lifecycle_audit.md`).
  - Devuelve `{ success: false, error: 'DUPLICATE_NAME' | 'DUPLICATE_CODE', parcelaId, nombre }`.
  - El error code se mapea a un mensaje user-facing en `getErrorMessage()` (string en español).
  - El classifier usa el **shape capturado en el spike (Sub-task 3.3.0)**: `error.code === '23505'` + parsing del campo `details`, NO substring matching de `error.message`.
- [ ] **(SC#5 — tombstone)** Tombstone sync funciona bidireccional:
  - Push: parcela local con `deleted_at != null` y `pending_sync=true` sube el `deleted_at` al server; tras éxito, `pending_sync=false` y `deletedAt` queda persistido local.
  - Pull: parcela en server con `deleted_at != null` marca el `deleted_at` local; la parcela deja de aparecer en `useParcelas`. NO se resurrecciona una fila tombstoneada por el server.
  - Conflict: si local tiene `pending_sync=true` con `deleted_at != null` (tombstone pendiente de subir) y server tiene la fila aún activa, el push gana — sube el tombstone. El pull subsiguiente no debe pisar el tombstone local pendiente.
- [ ] **(SC#7 — parcela-sync integration)** Test `parcela-sync.test.ts` cubre los escenarios E2E listados en Task 3.6.
- [ ] **(SC#5 — OrangeDot)** `usePendingSyncCount(plantacionId)` incluye parcelas (activas y tombstoneadas pendientes) en `pendingCount` global. La `PlantationCard` muestra OrangeDot si cualquier parcela bajo esa plantación tiene `pending_sync=true`.
- [ ] **Invariante atómico de Grupo preservado** (SYNC-PARC-04): el flujo atómico `sync_subgroup` RPC sigue funcionando para grupos. Subir un grupo con parcela aún pendiente es un orden lógico: el push siempre intenta parcelas primero; si todas las parcelas pendientes suben, los grupos se intentan después. Si una parcela falla, los grupos dependientes de esa parcela específica se saltan (no se suben) y se reportan como bloqueados.

### Task 3.2: `pullParcelas` en `pullService.ts` (con tombstones)

- **Files (modify):**
  - `mobile/src/services/sync/pullService.ts`
- **What:**
  - Crear función `async function pullParcelas(plantacionId: string): Promise<string[]>` espejada en `pullGroups` (post-16-01):
    - `supabase.from('parcelas').select('*').eq('plantation_id', plantacionId)` — sin filtro de `deleted_at`; el server envía la fila completa incluyendo el tombstone, y el cliente decide qué hacer.
    - Para cada parcela remota, decidir el upsert según el estado local:
      1. Consultar local: `ParcelaRepository.findById(remote.id, { includeDeleted: true })`.
      2. **Si local tiene `pending_sync=true`** (sea por update activo o por tombstone local pendiente): NO sobrescribir — preservar el estado local. Comentar en log: "pullParcelas: skipping {id} — local has pending changes". Push posterior subirá el cambio local, ganando.
      3. **Si local NO tiene pending o no existe**: hacer upsert con el shape del server, incluyendo `deleted_at` tal como viene del server. Si el server tiene `deleted_at != null`, el upsert local marca el tombstone (la fila persiste pero no aparece en `useParcelas`).
    - Implementación recomendada vía `db.insert(parcelas).values({...}).onConflictDoUpdate({ target: parcelas.id, set: { nombre: sql\`excluded.nombre\`, codigo: sql\`excluded.codigo\`, descripcion: sql\`excluded.descripcion\`, deletedAt: sql\`excluded.deleted_at\`, updatedAt: sql\`excluded.updated_at\`, pendingSync: sql\`CASE WHEN ${parcelas.pendingSync} = 1 THEN 1 ELSE 0 END\` } })`. El `CASE WHEN pending_sync=1 THEN 1 ELSE 0 END` preserva el flag local (memory `feedback_state_lifecycle_audit.md`).
    - **Refinamiento sobre el upsert ingenuo**: el `onConflictDoUpdate` solo se aplica si `pending_sync` local es `false`. Si es `true`, ejecutar un `findById` previo y saltar el upsert. Esto es necesario porque el `CASE WHEN` preserva el flag pero NO previene la sobrescritura de `deleted_at` con un valor del server. El check explícito previo evita pisar un tombstone local pendiente con la versión activa del server.
    - Retornar array de IDs de parcelas remotas (para que `pullGroups` pueda hacer su filtro `.in('parcela_id', ...)` si lo necesita — espejado con cómo `pullSubgroups` devuelve IDs para `pullTrees`).
  - Modificar `pullFromServer(plantacionId)` para llamar `pullParcelas` **ANTES** que `pullGroups`. Orden final:
    1. `pullPlantationMetadata`
    2. `pullParcelas` ← nuevo
    3. `pullGroups` (post-16-01 rename de `pullSubgroups`)
    4. `pullPlantationUsers`
    5. `pullPlantationSpecies`
    6. `pullTrees`
  - Mantener `pullParcelas` ≤20 líneas; extraer helper `upsertParcelaFromServer(p)` y `shouldSkipLocalPending(id)` si excede.
- **Why:** SYNC-PARC-01, D-16-12 (orden FK), D-16-19 (tombstones).
- **Verification:**
  - `npx tsc --noEmit` → 0 errores.
  - Unit test isolated (puede vivir en `sync-pipeline.test.ts`): mock supabase con 1 parcela remota; `pullFromServer` → fila aparece local con `pending_sync=false`.
  - Tombstone del server: mock supabase con parcela con `deleted_at != null` → pull → local marca `deleted_at`, parcela no aparece en `useParcelas`.

## Risks & Mitigations

1. **Riesgo:** El shape del error de Supabase puede cambiar entre versiones del driver `supabase-js` o entre versiones de postgres. **Mitigación:** El spike (Sub-task 3.3.0) ancla el shape en el momento de la implementación y lo documenta en código. El classifier tiene un fallback explícito `GENERIC_CONFLICT` cuando el parsing no encaja (drift). El test 5 de Task 3.6 cubre el fallback path. Si el shape cambia en una update futura, el classifier degrada a `GENERIC_CONFLICT` y el usuario ve un mensaje genérico — degradación segura, no crash silencioso.
2. **Riesgo:** El orden FK en pull falla si el server tiene un grupo cuya `parcela_id` apunta a una parcela que **acaba de tombstoneerse** del server (parcela con `deleted_at != null`, grupo aún sin tombstone). **Mitigación:** El upsert preserva `deleted_at` del server; el grupo con FK a una parcela tombstoneada es un estado válido en SQLite (FK constraint solo verifica que la fila exista, no que esté "viva"). Capturar con try/catch en `pullGroups` si emerge una FK violation y skipear el grupo huérfano con `syncLog.error`. Documentar como edge case raro.
3. **Riesgo:** Tombstone se sube exitosamente pero el siguiente pull (sin push previo en el mismo run) trae la versión activa anterior del server si la propagación server-side se demora. **Mitigación:** El orden de operaciones siempre es `push → pull` dentro de un `SyncService.run()`; el push del tombstone se completa antes del pull subsiguiente. Si un pull manual se ejecuta entre push fallido y retry, el `pending_sync=true` previene la sobrescritura (lógica de Task 3.2 — skip si local pending). Cobertura: escenario 11 de Task 3.6.
4. **Riesgo:** Test `parcela-sync.test.ts` se vuelve flaky por mock state no aislado entre tests. **Mitigación:** `beforeEach` resetea tanto la DB local (FK-ordered delete, incluyendo tombstones) como el mock Supabase (clear de los Maps internos). Verificar que cada test es self-contained (puede correrse solo con `--testPathPattern`).
5. **Riesgo:** `usePendingSyncCount` ahora tiene 3-4 queries reactivas; un re-render storm si las queries no debouncean. **Mitigación:** `useLiveData` ya tiene debounce interno (Phase 13). La query agregada vive en `pendingSyncQueries.ts` (Task 3.5) lo que permite optimizar a una sola query si emerge el problema. Validar en smoke test (Android) que abrir/cerrar la pantalla varias veces no genera lag perceptible.
6. **Riesgo:** La migration Supabase 014 se olvida al ejecutar el test E2E en CI. **Mitigación:** Documentar en `tasks/16-03-prereqs.md` el comando `supabase db push` o equivalente; idealmente, el `globalSetup` de Jest/Vitest la aplica automáticamente leyendo `supabase/migrations/`.
