## Goal

Cerrar PDEF-01..04: introducir un feature flag compile-time `AUTO_PARCELA_DEFAULT` (default ON, D-18-02) y aislar la lógica de "al crear una plantación, crear también `Parcela 1` (`P1`)" en un servicio nuevo `PlantationCreationService.ts` (D-18-03). El helper orquesta `createPlantation` (online) o `createPlantationLocally` (offline) + `createParcela` dentro de una transacción local Drizzle (D-18-04), marcando ambos rows con `pending_sync=true` para que el flujo de sync existente (Phase 16-03) los suba en orden de FK. Todos los puntos de inserción del trial llevan el comentario marker para remoción mecánica.

## Success Criteria

Mapea a ROADMAP Phase 18 success criteria:

- [ ] **SC#1** `mobile/src/config/featureFlags.ts` existe con la constante `AUTO_PARCELA_DEFAULT = true` y JSDoc explicando: qué controla, cómo desactivarla, qué pasa con plantaciones ya creadas (no backfill — D-18-07).
- [ ] **SC#2** Con flag ON, llamar a `createPlantationWithDefaultParcela(...)` (online u offline) deja en la DB local una plantación nueva + 1 parcela `nombre="Parcela 1"`, `codigo="P1"`, `descripcion=null`, `pending_sync=true`, vinculada por `plantacionId`.
- [ ] **SC#3** Toda la lógica del trial vive en `PlantationCreationService.ts` + 1 call site (`usePlantationAdmin.ts`); ambos lugares llevan el comentario marker. Remover la feature = borrar el archivo + 1 import + revertir el call site (mecánico, 1 commit).
- [ ] **SC#4** Con flag OFF, el helper crea solamente la plantación (online o offline) y no inserta ninguna parcela; el comportamiento es idéntico al pre-Phase-18.
- [ ] **SC#6** Tests unitarios cubren: flag value, helper flag=true (ambos rows + transacción), helper flag=false (solo plantación), rollback cuando `createParcela` retorna `{success:false}`.

## Risks & Mitigations

1. **Hook test (`usePlantationAdmin.test.ts`) rompe porque mockeaba `createPlantation` directamente.**
   Mitigación: actualizar el test para mockear `createPlantationWithDefaultParcela` o agregar mock del service.
2. **Pull/sync inadvertidamente invoca el helper y duplica parcelas en plantaciones bajadas.**
   Mitigación: el helper NO se importa en `services/sync/pullService.ts`; verificar con grep al final de Task 1.3. Documentar en JSDoc del helper que es solo para creación iniciada por usuario.
3. **`db.transaction` no soporta funciones async anidadas con repositorios que ya hacen `db.insert(...)` fuera de la tx.**
   Mitigación: `createPlantation`/`createPlantationLocally`/`createParcela` usan `db` global; envolver en `db.transaction` significa que si están "ejecutando dentro" no abren tx anidada. Si la verificación de unicidad falla, retornan `{success:false}` y el throw del helper revierte. Si en práctica las funciones internas no participan de la tx exterior (Drizzle SQLite implementation), aceptar best-effort + documentar (rollback parcial = plantación creada huérfana sin parcela — sigue siendo válida).
4. **Hardcode `"Parcela 1"` / `"P1"` colisiona si usuario ya creó manualmente una parcela "P1" antes de que el flag se active.**
   No aplica en práctica (el flag está ON desde día uno y no hacemos backfill — D-18-07), pero `createParcela` ya valida unicidad y retornaría `codigo_duplicate` → rollback limpio.
5. **Flag flip de true→false en build futuro: plantaciones viejas con "Parcela 1" siguen ahí.**
   Aceptado por diseño (D-18-07). Documentado en JSDoc de `featureFlags.ts`.
